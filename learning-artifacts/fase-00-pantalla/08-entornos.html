Entornos de Python

El infierno de dependencias es real. El entorno virtual es el remedio.

El problema

Un proyecto pide PyTorch 2.4. Otro pide PyTorch 2.1 porque su build de CUDA está fijo. Si instalas en el Python del sistema, subir uno rompe el otro. En aprendizaje automático pasa seguido: cada marco trae su CUDA, las librerías clavan versiones, y un pip install global pisa lo que había.

La idea

Cada proyecto tiene su propia carpeta de paquetes. El proyecto A puede tener torch 2.4 y el proyecto B torch 2.1, y no se ven.

Este curso ya tiene el suyo: .venv, con Python 3.12.16, NumPy, Matplotlib, Jupyter y PyTorch 2.15. Se activa así:

source .venv/bin/activate

El prompt cambia y which python apunta dentro de .venv. Para salir: deactivate.

Con uv

uv venv
source .venv/bin/activate
uv pip install torch numpy

uv init crea un proyecto con pyproject.toml. uv add torch numpy instala y deja un archivo de bloqueo, para que otra máquina instale las mismas versiones.

Errores típicos

  • Instalar en el Python global y creer que el proyecto está aislado.
  • Mezclar pip y conda en el mismo entorno.
  • Un PyTorch compilado para una CUDA más nueva que el driver de la máquina.
